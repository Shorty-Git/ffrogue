# Climhazzard original-data feasibility probe

Checked on 2026-10-22. No game code, commands, runtime assets or engine were
changed. Original-effect playback has not been achieved.

Follow-up: the [verified structural reader](bmb-structural-reader.md) now reads
block boundaries, four node types, two lifetime parameters and typed resource
tables without a commercial SDK. It supersedes heuristic resource-name scanning
in the probe tool. It still does not decode or play the complete effect.

## Verified source package

The existing character inspection report identifies Cloud form `207000105`,
ability `214820` (Climhazzard). The secondary SQLite snapshot reports 52 MP,
`moveType=1`, `motionType=1`, and attack data `4:100:2:2`. These remain raw
source values, not newly implemented combat behavior. The Android backup and
SQLite snapshot are different sources; compatible filenames do not establish
that their game versions or mechanics match.

The catalog composition refers to four unique original binaries:

| Original | Source placement |
| --- | --- |
| `atk_slash7_side_purple.bmb` | Target front, F0; two members with different source rotations |
| `atk_blow1_purple.bmb` | Target front, F0, within the same opening group |
| `atk_powergeyser_001_purple.bmb` | Target front, F20 |
| `eff_strobe_white_a50_f30.bmb` | Screen back, group F0 plus member offset F1 |

A separate F20 group contains sound data without visual members. The skill is
not just the newly recovered power-geyser effect.

All four exact binaries were extracted from the Android backup. The power-geyser
binary is 43,200 bytes, starts with `IBMB`, has version bytes `01010301`, and SHA-256
`285cd85f2d2bdc3e0b73d81087390a735529c1d5edd9d4475cbd40666ffaddf2`.

`tools/inspect_bmb_resources.py` scans null-terminated ASCII resource-name
candidates and matches them only against `effectResource` archive members.
It is **not** a scene parser: it does not decode emitters, curves, blend modes,
resource bindings or a complete dependency graph. Index entries are rechecked
against the archive before decompression; payload sizes and written hashes are
validated. Source versions stay in separate archive-named folders.

- Power geyser: 14 named candidates, all found and extracted.
- Whole four-binary package: 19 unique resources, 13 PNGs and six M3R models.
- Every candidate matched exactly one effectResource member in this backup.
- All 13 PNGs passed Pillow verification; the texture contact sheet was visually
  inspected. M3R files were extracted and hashed, not decoded or rendered.

Ignored receipts and files are under `tools/data/climhazzard-source/`:
`skill-source.json`, `summary.json`, `originals/`, `effects/*/resources.json`,
the staged resources, and `texture-contact-sheet.png`.

Reproduce the resource probe from the repository root after the CPK index exists:

```powershell
& $env:FFROGUE_PYTHON tools/inspect_bmb_resources.py --source tools/data/android-cpk-audit/exact-effects/atk_powergeyser_001_purple.bmb --index tools/data/android-cpk-audit/members.jsonl --output tools/data/climhazzard-source
```

## Actual renderer compatibility test

An isolated localhost probe used the installed Effekseer WebGL 1.80.7 SDK in
the in-app browser with a real WebGL2 context. It served only the SDK and the
one original BMB, not the Android backup or application state.

1. The SDK initialized and loaded its bundled `Resources/Laser01.efk` control:
   `isLoaded=true`, nonzero native effect pointer.
2. The original 43,200-byte `IBMB` payload was passed to the same context's
   `loadEffect(ArrayBuffer, 1)` function: `isLoaded=false`, native pointer zero.
3. The visible test page and saved `effekseer-compatibility.json` agree.

This demonstrates that our installed Effekseer loader does not directly accept
this original binary. It does not test BISHAMON, a converter, or visual fidelity.
No Climhazzard animation was generated by this probe.

## Tool acquisition and decision gate

The [official BISHAMON store](https://store.matchlock.co.jp/?___from_store=japanese&___store=english)
lists the authoring tool separately from an SDK described as a program library
and converter. The visible Personal SDK product targets DirectX11. The page also
contains older contest-license material; that is not evidence of a currently
usable SDK trial. The [official FAQ](https://www.matchlock.co.jp/faq/) distinguishes
the Personal and corporate SDK platform offerings.

The [bmake author's documentation](https://www.dna-softwares.com/article/1353)
describes compiling BMSLN to BMB through an existing SDK. It is not a BMB-to-
Effekseer converter or a standalone original-effect player. The inspected public
ExviusReborn tree contains Effekseer playback but no identified BMB converter.
Search did not establish a compatible downloadable original-BMB player.
GitHub repository API searches were rate-limited (HTTP 403); this is not proof
that no community implementation exists.

Do not buy an authoring license or migrate the game based on these listings.
The next external compatibility question is specific:

> Can your available SDK load an existing Android FFBE IBMB binary with header
> bytes `49 42 4d 42 01 01 03 01`, plus its original PNG and M3R resources,
> without the BMSLN authoring project? Can that configuration be evaluated on
> Windows and rendered to transparent frames for an offline asset pipeline?
> Which SDK version and license are required?

No vendor message was sent, account created, software purchased or SDK installed.
The alternative is developing a BMB/M3R decoder and renderer, which is a separate
reverse-engineering milestone rather than a small format conversion. A runtime
rewrite is not justified by the current evidence: the proven blocker precedes
the choice of game engine.
